## Verdicts transverses

1. **Deux protocoles distincts coexistent** pour les recettes :
   - **« Propriétés preset » (0xD18C/0xD18D/0xD18E-0xD1A5)** — boîtiers récents seulement. Confirmé : X-S10, X-H2, X-T5, X100VI, X-S20 (+ liste Fuji X Weekly App : X-Pro3, X100V, X-T4, X-E4, X-T30 II, etc.). **Explicitement absent sur X-T30 gen 1 et X-T3** (Fuji X Weekly App : « not able to connect » ; aucun projet au monde ne le revendique sur X-T30 gen 1).
   - **« Blob de réglages » (backup/restore, objet handle 0, format 0x5000)** — le chemin des anciens boîtiers, utilisé par X Acquire officiel, rétro-ingéniéré par grawji (**vérifié sur X100F et X-T3**) et libfuji. Les banques C1-C7 (avec noms !) vivent DANS ce blob. **C'est notre voie pour le X-T30.**

2. **Le transport WPD n'est pas en cause** : fudge/libfuji utilise sous Windows exactement le même passthrough WPD que xt30-probe (via libwpd), sans aucun quirk ni filtrage documenté. Aucune source ne rapporte un driver MTP Windows filtrant GetDevicePropValue.

3. **Notre scan du 31/08 portait la signature du mode MTP/card-reader** (DeviceInfo minimal, opcodes MTP 0x9801-0x9805, propriétés MTP standard 0xD406/0xD407, 0xD16E illisible = le critère exact de libfuji pour dire « pas en RAW CONV »). Le mode du menu n'était pas confirmé — à refaire en mode confirmé avant tout verdict définitif.

4. **Conversion RAW (0xD185)** : fonctionne sur X-T30 (rawji l'a testé) — mais c'est un profil de développement volatile, PAS les banques C1-C7. Utile plus tard pour la prévisualisation des recettes rendue par l'appareil lui-même.
